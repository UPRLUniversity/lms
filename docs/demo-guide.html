0How to use this guide

Read this page once before you start. It will save you every avoidable surprise tonight.

  • Everything here has been executed against the real running app, not written from the code. Where a screen is quoted, that is what it actually says.
  • Follow the numbered steps literally. Each one names the exact menu item, tab or button to click. Grey boxes like Teaching are things you click in the left sidebar; every step also gives a fallback URL you can paste into the address bar if you lose your place.
  • Gold boxes are copy-paste. Anything you need to type during the demo is in a gold box, ready to copy.
  • Italic lines marked Say: are optional talking points — the "why this matters" for your teammate.

E-mail addresses (student1@uprl.test …) and course codes (PRL101 …) are stable forever. This guide always identifies people by e-mail. The names printed in tables here are only what the seed produced at the time of writing.

1Pre-flight — get the machine ready

Do this ~10 minutes before your teammate joins. It takes about 3 minutes of typing and 2 minutes of waiting.

Step 1 — Open a terminal in the project folder

cd "c:\Users\OLASQUARE\Desktop\My Projects\UPRLUniversity\lms"

Step 2 — Reset the demo data to a known-good state

This wipes and rebuilds the database so everything in this guide matches exactly. It takes about 90 seconds — start it, then read on.

php artisan migrate:fresh --seed

You are looking for a final line similar to:

ReportingDemoSeeder: 84 historical enrolments, 292 lesson-progress rows,
19 skipped to respect course capacity.

Step 3 — Build the front-end assets

Only needed if you have changed any file under resources/ since the last build. If in doubt, run it — it takes ~45 seconds.

npm run build

Step 4 — Start the server

Leave this terminal window open and running for the whole demo.

php artisan serve

Then open http://127.0.0.1:8000 in your browser.

Mail has already been set to "log" mode for you Your .env previously pointed at a live SMTP server and sent mail synchronously. That made every notifying action (approving an enrolment, posting an announcement, grading a submission) pause for ~1.5 seconds — and it would have failed outright if tonight's network blocks port 465. MAIL_MAILER is now log: actions are instant, nothing depends on the network, and the e-mail bodies are still written to storage/logs/laravel.log if you want to show one.

To restore live sending after the demo: open .env, change MAIL_MAILER=log back to MAIL_MAILER=smtp, then run php artisan config:clear.

Step 5 — Browser setup (60 seconds, worth it)

  1. Open a normal window — this is Window A (you will be the student here).
  2. Open an incognito / private window — this is Window B (you will be staff here). Put them side by side, or use two virtual desktops you can flip between.
  3. Zoom both to 110–125% (Ctrl + +) so the room can read them.
  4. Close any other tabs. Hide your bookmarks bar.
Optional — only if you want to demo the queued-export path (Act 9, step 8) That feature only triggers above a row threshold, and the demo dataset is deliberately small. To make it demonstrable, add this line to .env, then run php artisan config:clear:
REPORTS_QUEUE_THRESHOLD=50
Remove the line (or set it back to 2000) afterwards. No queue worker is needed — QUEUE_CONNECTION is sync, so the job runs immediately.

Step 6 — Optional confidence check

If you want to open by stating the test count, run this first (takes ~5 minutes, so do it early or skip it):

php artisan test

Expected: 447 passed.

2The system at a glance

One page you can hold in your head. Useful if your teammate asks "so what is this?"

UPRL LMS is a Learning Management System for a single Nigerian university — the University of Public Relations and Leadership. It covers the full lifecycle: a public course catalogue, enrolment (with approvals, capacity and waitlists), an authoring toolkit for instructors, a distraction-free learning player, quizzes and assignments with rubric grading, a gradebook mapped to Nigerian grading scales, verifiable PDF certificates, forums and messaging, notifications, and an exportable reporting suite.

The five roles

RoleWhat it can do
Super-adminEverything, without exception. Bypasses every permission check. Cannot deactivate itself.
AdminRuns the university: people, faculties & departments, grade scales, certificate templates and the registry, the publishing decision on any course, enrolment approvals, bulk import, forum moderation, and the full report centre.
InstructorBuilds and teaches their own courses: curriculum, question bank, assessments, assignments & rubrics, grading, learner progress and per-course analytics, announcements, and the approval queue for courses they lead.
StudentBrowses the catalogue, enrols, learns, takes assessments, submits assignments, discusses in forums, messages staff, sees grades, earns certificates.
AuditorA read-only observer for governance. Sees people, courses, rosters, progress, grading, certificates and reports — and holds no ability to create, edit, approve or delete anything, by construction rather than by hiding buttons.

Three architectural claims worth making out loud

  • Authorization is never inline. Every permission decision lives in a Policy class. There is not a single if (user is admin) in a controller or a template. The auditor is read-only because it holds only view permissions — not because buttons were hidden.
  • Rules are enforced on the server, not in the browser. Sequential lesson locking, the exam timer, capacity, and the answer key are all server-side. You will prove two of these live by pasting a URL that should work and watching it be refused.
  • History is immutable. A submission version, a grade snapshot and an issued certificate are written once and never rewritten. Editing a rubric or a grade scale afterwards cannot retroactively change a student's record.

8Act 5 — Assessment & grading≈ 9 min

Goal: show a real exam engine and a real marking workflow — including the parts a student must never be able to cheat.

Stay as student1@uprl.test in Window A.

  1. Open the exam. Paste:
    http://127.0.0.1:8000/learn/prl101-foundations-of-public-relations/assessment/final-exam
    The start screen states the rules up front: 6 questions · 20 min · pass mark 60% · 2 attempts left.
  2. Start it. Click Start attempt. The runner is one question per screen, with a question navigator across the top, a Flag control, and a live countdown.
  3. Answer three or four questions, moving with the numbered navigator. Point out the variety as you go — true/false, single-answer, multi-select, a drag-free matching grid with dropdowns, a fill-in-the-blank. The counter at the top updates to "4 of 6 answered" as you go: every answer is saved to the server the instant you pick it.
  4. Prove the timer is server-side. Press F5 to reload the page mid-exam.
    • Your answers are still there.
    • The questions are in the same order with the same shuffled options.
    • The clock has kept running — it did not reset.

    Say: The deadline is a timestamp on the server. Refreshing, closing the laptop or editing the page cannot buy a single extra second. And the correct answers are never sent to the browser before you submit — you can open developer tools and they simply aren't there.

  5. Submit. Answer the rest, click Submit, confirm. You land on the result screen immediately:
    • A percentage, a Passed / Not passed verdict, and points scored.
    • A full review: every question, your answer, whether it was right, and the explanation.
    • On the matching question, note partial credit — for example 1/4 — rather than all-or-nothing.

    Say: Whether a student may see the answers at all is a per-assessment setting: immediately, only after the assessment closes, or never.

  6. The instructor's side. Switch to Window B as instructor1@uprl.test and click Grading.
    Fallback URL: /manage/grading
    There are two tabs. On Assessments you'll find the essay attempt awaiting a human. Click Grade: the student's answer sits beside the marking panel, with the author's guidance notes for the marker. Award points and add feedback.
  7. Assignment grading. Click the Assignments tab. Fallback URL: /manage/grading/assignments
    Note the queue: one submission flagged Late, one that is v2 — a resubmission after being sent back. Filter by course, assignment and status.
  8. Grade against a rubric. Click Grade on the Crisis communication case study submission.
    • Left: the student's work, with PDFs and images previewed inline.
    • Right: the rubric grid. Click a performance level on each criterion — the total recalculates as you go.
    • Add feedback and click Grade & next, or use Return for resubmission with a note.
    Feedback you can paste: Strong situation analysis and a well-judged holding statement. Tighten the evaluation section — name the specific measures you would report to the Vice-Chancellor, and say when you would report them.

    Say: The grade stores a snapshot of the rubric exactly as it was when marked. Editing or deleting that rubric later can never rewrite a student's breakdown. And the server is the only scorer — the browser never computes a mark.

  9. The gradebook. Go to:
    /manage/courses/prl101-foundations-of-public-relations/gradebook
    A students × items matrix. Items still awaiting a mark show Pending and are excluded from the percentage. The Export button offers CSV, Excel and PDF.
  10. Grade scales. As an admin, Grade scales (fallback: /admin/grade-scales) holds NUC Standard (5.0) as the default and a 4.0 Scale alternative. Open the NUC scale to show the bands (A 70–100% → 5.0, down to F).

    Say: A course can override which scale it uses. But a grade already recorded freezes the whole scale into itself — so changing a band next semester cannot retroactively regrade last semester's students.

    • Upload it back. You get a preview, not an import — every row is checked and flagged: unknown e-mail, unknown course code, duplicate within the file, already enrolled.
    • Only then does Confirm import commit the valid rows. Files over 100 rows are handed to a background queue.

    If you'd rather paste your own file, this content is valid and mixes good rows with deliberate errors so the validation actually shows something:

    email,course_code student20@uprl.test,PRL101 student21@uprl.test,LDS201 student22@uprl.test,PRL220 nobody@uprl.test,PRL101 student23@uprl.test,ZZZ999 student20@uprl.test,PRL101

    Row 4 is an unknown person, row 5 an unknown course, row 6 a duplicate of row 2 — all three will be flagged and skipped.

  4. Export. Back on any roster, click Export CSV to download the current roster.

10Act 7 — Certificates & public verification ★≈ 5 min

Goal: a real, printable, independently verifiable credential. This lands well with non-technical audiences.

  1. Window A — sign in as a student who holds one:
    E-mail: student14@uprl.test Password: password
    Click My Certificates. Fallback URL: /certificates
  2. Download it. Click Download and open the PDF. Point at:
    • The UPRL crest, the gold border and the sunburst watermark.
    • The student's name, the course, the completion date and the grade.
    • The serial number — printed on the certificate, in the form UPRL-2026-XXXXXX.
    • A QR code that links to the public verification page.
    Write the serial down now Read the serial off this PDF and keep it to hand — you need it in step 4, and serials are regenerated on every re-seed so no printed value would be correct.
  3. Note the diacritics. If the student's name carries Yoruba or Igbo marks (Ọ, ẹ, ị), they render correctly — the PDF embeds proper Unicode fonts rather than falling back to the ASCII base fonts that would print question marks.
  4. Public verification — the point of the whole feature. Open a third, signed-out window (or just use the incognito one after logging out) and go to:
    http://127.0.0.1:8000/verify
    Type in the serial you noted. You get a Valid certificate result showing the holder, the course and the issue date.

    Say: No account, no login. An employer in Lagos can verify a UPRL credential in ten seconds — or just point a phone camera at the QR code on the printed certificate.

  5. Show a failed lookup. Enter an obviously fake serial:
    UPRL-2026-ZZZZZZ
    You get a polite "we couldn't find that certificate".

    Say: The wording is identical for every kind of miss, and the endpoint is rate-limited — so nobody can probe it to work out the serial format or guess their way to a hit.

  6. Revocation. Window B as admin1@uprl.test → Certificates. Fallback URL: /admin/certificates
    • The full registry, searchable by student, course or serial. One row is already Revoked — copy that serial and check it on /verify: it reports the certificate is no longer valid, and deliberately does not say why.
    • Note the "Completed, not yet issued" panel at the top, which catches anyone who finished a course without a certificate, with a one-click Issue certificate button. Click it on one row to issue a certificate live.
    • Re-issue re-renders the PDF but keeps the same serial and URL — so a certificate already printed and handed out never stops working.
  7. Templates. Click Certificate templates — two designs (Classic and Modern), with the signatory name, title and signature image configurable, and a live Preview.

    Say: An issued certificate freezes its template and its grade at the moment of issue. Redesigning the template next year changes nothing that's already in someone's hands.

15If something goes wrong

Everything in this guide was executed against the running application, so none of it should surprise you. But if it does:

SymptomDo this
Anything at all looks wrong and you have 2 minutes Re-run php artisan migrate:fresh --seed. It restores every state described in this guide, and takes ~90 seconds. This is the universal fix — do it between runs if you present twice.
A page looks unstyled, or a button does nothing The compiled assets are stale. Stop the server, run npm run build, restart with php artisan serve, then hard-reload the browser with Ctrl+Shift+R.
"Page Expired" after submitting a form The page sat open too long and the security token expired. Reload the page and submit again. If it persists, sign out and back in.
You are unexpectedly signed out Sessions last 2 hours. Just sign in again — nothing is lost.
The waitlist doesn't promote anyone The course must be genuinely at capacity first. Check the roster meter reads 3 / 3 before withdrawing. If it doesn't, re-seed.
A certificate serial from this guide doesn't work Expected — serials regenerate on every seed. Read the current one off the certificate PDF or the registry at /admin/certificates.
A student's name doesn't match this guide Expected — names are randomised per seed. Always go by e-mail address.
The queued-export demo downloads instead of queueing You skipped the optional pre-flight step. Add REPORTS_QUEUE_THRESHOLD=50 to .env and run php artisan config:clear.
Port 8000 is already in use Run php artisan serve --port=8001 and use http://127.0.0.1:8001 throughout.
You need to see an e-mail the system "sent" Mail is in log mode. Open storage/logs/laravel.log and scroll to the bottom — the full rendered message is there.
Two things in the interface that are intentional, in case someone asks 1. The Settings item at the bottom of the admin sidebar is greyed out and marked Soon. It is a deliberate placeholder for a future section, not a broken link.
2. On the admin dashboard, the enrolment trend's final bar is much taller than the rest. That's because all the "live" demo enrolments are dated today while the historical ones are spread across the previous eleven months. It reads as growth, which is fine — just don't claim it as a real trend.

16Scope, roadmap & quick reference

What is deliberately not built yet

Naming these yourself is far better than being asked. They are roadmap, not gaps:

  • A settings/configuration area for institution-wide preferences — the placeholder is visible in the sidebar.
  • Live notifications over websockets. The bell polls every 60 seconds today, which is sufficient; real-time push is a deliberate later upgrade.
  • Self-hosted video with access control. Video is embed-first (YouTube/Vimeo). If protected video is ever needed, it should go to a dedicated video host, not general file storage.
  • Payments and fees. Never in scope for this build.
  • Mobile applications. The interface is fully responsive from 375px upward, but there is no native app.
  • Automated profanity filtering in forums — explicitly out of scope; moderation is the report queue plus server-side HTML sanitising.
